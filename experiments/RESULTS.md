- **2026-10-10 — Two tooling errors found while reading the first real R0 runs (Claude). Both fixed in `08_r0.sh` / `09_r0_report.py`; affected runs moved to `experiments/r0/runs_superseded_ts_syntax/`.**
  1. **Device order is remote-first.** `src/llama.cpp:275` ("add RPC servers at the front of the list to minimize network transfers"). Verified from `llama-cli --verbose` on the Air (requester) with the M5 as worker: `-ts 0,1` → all 29 layers `assigned to device MTL0` (4168 MiB local, RPC buffer 0); `-ts 1,0` → all 29 on `RPC0` (4168 MiB remote); `-ts 1,1` → layers 0–14 on `RPC0` (1996 MiB), 15–28 on `MTL0` (2172 MiB). ARCHITECTURE.md, `04_run_two_machines.sh`, R0_PROTOCOL, the runbook and the report's verification logic had it backwards; corrected.
  2. **`llama-bench -ts` syntax.** `llama-bench` uses `/` between devices and `,` between *sweep configurations*. `-ts 0,1` therefore ran two configs — `[0]` (all-zero → default memory-proportional split) and `[1]` (all on device 0 = the RPC worker) — and `-ts 1,1` ran `[1]` twice. Each `bench.json` holds four entries. The historical `05_bench.sh` had the same bug, so any Table-B row ever produced by it carried a wrong label.
  **What the superseded runs still show** (Air M3 requester, M5 worker, Wi-Fi, ping avg ≈ 12 ms / max 50–78 ms, same SHA and model hash on both): M5 local (Table A) pp256 = 683 ± 30, tg64 = **26.3 ± 0.3** t/s. All layers on the M5 *remote* (`[1]` config, 3 runs): pp256 = 309–331 (one run 488), tg64 = **6.6 / 7.4 / 9.9 / 10.3** t/s. Default split ≈ 60 % remote / 40 % local (`[0]` config, 2 runs): pp256 = 203–218, tg64 = 8.2 / 9.7 t/s. So decode on the *same* M5 GPU went from 38 ms/token local to ~100–150 ms/token when driven over one Wi-Fi hop — **an added ~60–110 ms per token on a link whose ping RTT is ~12 ms**, i.e. several round-trips' worth per token, not one. Candidate explanations to separate in R0 on Ethernet and in R1: Wi-Fi jitter (p95 was 4–6× the mean), the number of RPC messages per token (`set_tensor` of inputs, serialized `graph_compute`, `get_tensor` of logits), and per-command serialization cost. Not a result yet — the runs were mislabeled and the link was noisy — but a strong pointer that H1's "boundaries × transfer cost" must count *messages per token*, not RTTs.
  **Reading under team decision T1 (same day):** this is **not** a latency problem to solve — the slow link is the premise. It is an **efficiency property of the substrate**: if llama.cpp RPC spends k serial messages per token, `E(2)` drops because of the protocol, not the network, which argues for our own transport on efficiency grounds. **Corrections from I010 (same day), accepted:** (1) the 100–150 ms/token figures should be read from `avg_ns/64` of each record (136 / 104 / 103 / 152 ms), not from the inverse of mean tok/s; (2) the gap is *remote configuration* vs *local*, not an isolated network cost — it bundles requester, staging, protocol and network, and an Ethernet point changes RTT, jitter and bandwidth together, so it will not by itself separate "network" from "protocol"; (3) three RPC commands are not three RTTs — `SET_TENSOR`/`GRAPH_COMPUTE` are sent without waiting, and a repeated graph is sent as a 4-byte `GRAPH_RECOMPUTE` (`ggml-rpc.cpp:1015–1034`), so `k` must come from a trace, not from counting command names; (4) in the all-remote split the **output layer is remote too** (log: 28 blocks + output on RPC0), so every token returns `n_vocab × 4 B` ≈ 608 KB of float32 logits — ~17–21 ms at 230–285 Mbit/s before anything else — i.e. **bandwidth cannot be excluded as a decode factor**, and the planner should keep the output layer on the requester (llama.cpp's RPC-first default ordering does exactly that; our `1,0` overrode it). Next experiments, in order: corrected Table B; the capacity test — the same 32B model *first locally on each Mac* under a declared memory policy (the 12.1/18.2 GB figures are Metal's soft working-set recommendations; the machines have 16/24 GB), then split; and split-vs-independent-replicas at 1/4/8 requests on a model that fits on each machine.

- **2026-10-10 — First RPC command trace (R3c), worker M5 with `GGML_RPC_DEBUG=1`, requester Air, two `08_r0.sh placement` runs of 8 tokens each (`experiments/r0/worker_logs/20261010-171240_MMF4FWRG4R_worker_MTL0.log`, parsed by `12_rpc_trace.py`).** Two compute sessions in one log: session 1 = `1,0` (full graph, n_nodes 957, output layer remote), session 2 = `1,1` (n_nodes 510, 15 layers remote, output local).
  **Per steady-state decode step (median of the 3 tail steps):**

  | split | commands/step | of which waits for a reply | bytes in (`set_tensor`) | bytes out (`get_tensor`) | recompute share (tail) |
  |---|---|---|---|---|---|
  | `1,0` output remote | 8 = 6 set_tensor + 1 graph_recompute + 1 get_tensor | **1** (get_tensor) | ~14.9 KB | **608,256 B** (= 152,064 × 4, full fp32 logits) | 0.67 (prefill + warm-up were full `graph_compute`) |
  | `1,1` output local | 7 = 5 set_tensor + 1 graph_recompute + 1 get_tensor | **1** | ~14.9 KB | **14,336 B** (= 3,584 × 4, one hidden state) | 0.67 |

  Load phase: weights arrived mostly via `set_tensor_hash` (130 cache hits — the worker's `-c` cache from earlier runs worked), only ~470 MB (`1,0`) / ~252 MB (`1,1`) raw. **Reading (I010 §4 answered by measurement, not by counting names):** per token the substrate issues one blocking round trip (`get_tensor`), the rest is fire-and-forget on the same TCP stream, and the graph is re-sent only when its shape changes (`GRAPH_RECOMPUTE` otherwise). So `k_waits ≈ 1`, not 3+. What differs between the two splits by **42×** is bytes out: 608 KB vs 14 KB per token — at the measured 230–285 Mbit/s that is ~17–21 ms vs ~0.5 ms per token of pure transfer. **This is the first measured planner rule: keep the output stage on the requester** (llama.cpp's RPC-first ordering does it by default; `1,0` overrides it). Pre-registered expectation for the corrected Table B on this Wi-Fi: `1,1` decode ≈ 0.5×38 + 0.5×50 + ~13 ms (one RTT + 14 KB) ≈ 57 ms/token ≈ 17 t/s before jitter; `1,0` ≈ 38 + 12 + 20 ≈ 70 ms/token ≈ 14 t/s before jitter — the September-style 100–150 ms would then be mostly Wi-Fi tail latency, which the per-request spread will show. Limits: 8-token runs (tail of 3 steps), requester-side waiting not traced, debug logging itself not costed.
